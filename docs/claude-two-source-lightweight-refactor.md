# Claude 两来源轻量化重构方案

## 1. 目标

最终只保留两种 Claude 额度来源：

1. **BalanceBar Mod**：主要实时来源。
2. **官方 OAuth Usage API**：低频保底校准、reset 兜底、手动刷新和异常恢复。

Claude Code statusLine、Bridge、安装器、恢复逻辑和相关设置最终全部删除。Desktop Chat/Cowork 和 Web 暂不作为 Mod 的覆盖目标，继续依靠官方 OAuth 的账号级数据。

## 2. 已确认的产品规则

- 额度的新旧以数据产生时间为准，即 `observedAt` 或来源的 `updated_at`；BalanceBar 收到时间只用于诊断。
- 同一账号、同一 reset 周期内，用量不允许倒退。
- 如果 reset 时间发生变化，进入新周期，可以接受更低用量。
- Mod 数据完整、账号和周期可确认时，可以直接建立新周期。
- 完整的新周期 Mod 数据直接显示 `实时 · Mod`，不显示“待官方确认”。
- Mod 被卸载后，不再显示实时状态；保留最后读数和数据产生时间，显示现有的带警告时间的过期样式。
- Mod 重新安装后，收到第一份新的可信快照前，不恢复“实时 · Mod”。
- Mod 和 OAuth 同时存在时，按数据产生时间较晚且通过校验的读数显示。
- Mod/statusLine 冲突只写 error 级日志，暂不在 UI 展示。
- OAuth 不因每一条本地更新而请求；本地来源持续有效时，最多每 15 分钟进行一次保底校准。
- 本地来源距离有效期结束约 10 秒时，提前进入 OAuth 预取窗口。
- 用户手动刷新时绕过 Mod 有效期限制，直接尝试 OAuth。
- 普通网络错误和解析错误每 1 分钟重试。
- 401 暂停，直到凭据版本发生变化。
- 429 按 5 分钟、10 分钟、15 分钟、15 分钟、之后持续 15 分钟的节奏重试。
- 正在请求时不重复发起请求。
- 仍保留账号身份、epoch、reset、时间顺序和同周期单调性校验；轻量化不能牺牲这些准确性保护。

## 3. Main 当前架构

当前 Main（`956eb4cb`）仍是三来源架构：

```text
官方 OAuth ───────────────┐
Claude Code statusLine ──┼→ ClaudeQuotaPipeline
BalanceBar Mod Inbox ────┘         ↓
                              QuotaMergeEngine
                                ↓       ↓
                         StatusSlot  FetchScheduler
```

### 官方 OAuth

- A 级数据，负责账号级 5h/7d 使用量。
- 由 `FetchScheduler` 统一处理手动、定时、reset confirmation 和其它请求。
- Main 已包含 PR #622 的提前约 10 秒预取。
- Main 仍保留普通失败退避、401 暂停、429 冷却和本地来源新鲜度抑制。

### Mod

- 通过 Inbox 接收 Schema v1 快照。
- 快照提供 `updated_at`、5h/7d、`resets_at` 和 email hash。
- 已有账号哈希、epoch、重放、旧文件、周期和倒退保护。
- 覆盖 CLI、`claude -p`、Agent SDK、并行会话和 Desktop Code。
- 不覆盖 Desktop Chat/Cowork 和 Web。

### statusLine

- 当前仍是独立的 B 级本地来源。
- 有 Bridge、socket、会话登记、安装/恢复/卸载和设置开关。
- 与 Mod 共同进入 `receiveNative → QuotaMergeEngine`。
- 目标重构完成后整条路径删除。

## 4. 当前 Main 与目标的主要差距

### 4.1 B 级数据依赖 A 级基线

`QuotaMergeEngine` 当前要求 B 级读数已有同窗口 A 级基线。官方未登录时，Mod 的有效变化会被拒绝。这与目标“Mod 完整数据可以独立实时显示”冲突。

需要改为：

- 同账号、同 epoch、reset 信息完整且自身时间有效的 Mod 数据可以建立初始显示；
- 同周期继续执行单调性检查；
- reset 变化允许新周期低值；
- OAuth 恢复后仍可校准和纠正 Mod；
- 缺少周期信息时不能假定新周期。

### 4.2 调度器还需要明确“15 分钟保底”

当前调度器主要使用本地来源新鲜度和校准上限抑制 OAuth。目标需要增加明确的账号级保底时间：

- 本地来源持续有效时，OAuth 最迟 15 分钟尝试一次；
- 预取提前量约 10 秒；
- 手动刷新绕过本地新鲜度；
- 401、429、请求中状态仍然优先阻止请求。

### 4.3 普通错误重试策略需要统一

目标要求普通网络错误和解析错误都按 1 分钟重试。401 和 429 继续单独处理，不能被普通错误重试覆盖。

### 4.4 Mod 卸载状态需要与可信数据分离

卸载后，最后一条 Mod 数据可以保留用于显示历史时间，但不能继续让调度器认为 Mod 正在提供实时数据，也不能继续抑制 OAuth。

### 4.5 statusLine 删除前需要验证 Mod 能力

statusLine 最终删除，但应先完成 Mod 的最小真实 Gate，确保删除后不会丢失目标范围内的数据。

## 5. 建议的 Issue 流

### Issue A：定义并实现两来源合并规则

范围：

- 移除 B 级必须依附 A 级基线的前置条件；
- 允许完整 Mod 数据独立建立窗口；
- 保留账号、epoch、reset、时间顺序和同周期单调性；
- 同周期倒退拒绝；
- reset 变化后允许新周期低值；
- Mod 与 OAuth 冲突按数据产生时间处理；
- 冲突写 error 日志。

验收：

- 无 OAuth 登录时，Mod 新数据可显示；
- Mod 新周期完整数据直接显示为实时；
- 同周期 40% 不会被较新的 35% 覆盖；
- reset 变化后 35% 可以覆盖旧周期 40%；
- 旧时间数据不能覆盖新时间数据；
- OAuth 恢复后可以纠正 Mod。

### Issue B：重构 OAuth 调度和错误恢复

范围：

- 本地来源有效时最多 15 分钟一次 OAuth 保底；
- 有效期结束前约 10 秒预取；
- 手动刷新绕过本地有效期；
- 网络/解析错误 1 分钟重试；
- 429 使用 5/10/15/15/15 分钟策略；
- 401 只在凭据变化后解除；
- 正在请求时合并请求；
- 日志记录请求原因和跳过原因。

验收：

- Mod 持续更新时 OAuth 不会每次事件都请求；
- OAuth 最迟按保底策略尝试；
- 预取不会突破最小请求间隔；
- 网络恢复后约 1 分钟内重新尝试；
- 429 不被普通重试覆盖；
- 手动刷新在 Mod 有效时仍可到达 OAuth。

### Issue C：Mod 生命周期和过期状态

范围：

- 外部卸载立即取消 Mod 的实时资格；
- 保留最后读数和产生时间；
- 显示现有警告时间样式；
- 卸载后不再抑制 OAuth；
- 重装后第一份新快照到达前不恢复实时状态；
- 高级设置中的 Mod 有效期继续作为数据有效期来源。

验收：

- 外部卸载后不显示“实时 · Mod”；
- 最后数据时间仍可见；
- 卸载期间 OAuth 可以接管；
- 重装但没有新数据时不会复用旧实时证据；
- 新快照到达后恢复实时。

### Issue D：验证 Mod 并删除 statusLine

前置：

- Issue A、B、C 完成；
- Mod Gate 通过。

范围：

- 删除 `ClaudeStatusLineSource`；
- 删除 Bridge/helper；
- 删除安装、恢复、卸载和设置开关；
- 删除 statusLine 测试、本地化和设置入口；
- 从 `ClaudeQuotaPipeline` 移除 statusLine 接线；
- 管线最终只保留 Mod + OAuth。

必要 Gate：

- CLI 多次真实变化；
- 多个并行会话；
- Desktop Code；
- 应用重启；
- reset 前后；
- 账号切换；
- Mod 停用、卸载、重装；
- Mod 快照到菜单展示延迟；
- OAuth 请求次数明显下降。

## 6. 暂不处理

- Desktop Chat/Cowork 的前台监听；
- Web 浏览器监听；
- CC Switch 作为额度来源；
- HUD 作为独立额度来源；
- 用量估算；
- 新增第二套网络轮询器；
- 修改 Codex、Grok、菜单栏 C/扣图标和无关 Dashboard。

## 7. 主要风险

1. Mod Schema v1 没有 organization UUID。同邮箱不同组织且 reset 时间完全一致时，理论上仍有残余归属风险。
2. 如果 Mod 的 `session.measure` 在某些 Claude Code 运行模式下不触发，OAuth 只能在保底周期后修正。
3. Mod 覆盖 CLI 和 Desktop Code，不覆盖 Web/Chat/Cowork；只保留 Mod 不能解决这些来源的即时变化。
4. 删除 statusLine 后，任何 Mod 事件缺失都会更依赖 OAuth 保底。

## 8. 当前决策

目标不是简单地把“最后到达的数据”显示出来，而是：

> 在数据通过账号、epoch、reset、时间和单调性校验后，显示产生时间最新的可信读数；Mod 负责低延迟实时数据，OAuth 负责低频保底和纠正，statusLine 最终退出。

## 12. 验收 Gate

### Gate 1：合并规则

- 无 OAuth 登录时，Mod 变化能显示；
- 同周期较低读数被拒绝；
- reset 变化后的较低读数被接受；
- 旧产生时间不能覆盖新产生时间；
- 完整新周期显示 `实时 · Mod`；
- 缺失 reset 时间时不会错误建立新周期；
- OAuth 恢复后可以纠正 Mod。

### Gate 2：调度器

- Mod 持续更新时，OAuth 请求不会按每条快照重复发生；
- 最迟按 15 分钟保底；
- 本地过期前约 10 秒进入预取窗口；
- 手动刷新可以绕过本地有效期；
- 网络/解析错误约 1 分钟后重试；
- 429 不被普通失败重试覆盖；
- 401 不空转；
- 并发请求被合并。

### Gate 3：Mod 生命周期

- 外部卸载后立即失去实时资格；
- 最后数据时间仍然显示；
- 卸载后 OAuth 可以接管；
- 重装但没有新快照时不会复用旧实时状态；
- 新快照到达后恢复实时。

### Gate 4：删除 statusLine 前的 Mod 验证

- CLI 多次产生真实变化；
- `claude -p` 至少验证一次；
- Agent SDK 至少验证一次；
- 两个或更多并行会话；
- Desktop Code；
- 应用重启和睡眠唤醒；
- reset 前后；
- 账号切换；
- Mod 停用、卸载、重装；
- 记录快照产生到菜单更新的延迟；
- 对比重构前后的 OAuth 请求次数。

## 13. 对 statusLine 删除的建议

statusLine 可以删除，但不应在合并规则和调度器尚未稳定前直接删除。最小风险顺序是：

1. 先让 Mod 在两来源管线中独立建立和更新数据；
2. 再切换 OAuth 到 15 分钟保底；
3. 完成 Mod Gate；
4. 删除 statusLine 生产接入和全部实现；
5. 运行完整回归，确认 Claude 只剩 Mod + OAuth。

这不是保留 statusLine 兼容层，而是把“确认 Mod 足够可靠”和“删除冗余来源”分成两个可验证步骤。
